# Boyscout findings — 2026-08-26 14:35

Context: found while executing the Airflow 2.11 → 3.3.1 migration (`design_docs/AIRFLOW3_B_MIGRATION_GUIDE.md`)
in a dirty working tree on top of `4af6de56` (branch `airflow_3_ready_IV`). Nothing committed.

## 1. `streamlit` and Airflow 3 cannot share one python env 🔴

`webapp/requirements_webapp.txt:4` pins `streamlit==1.55.0`, whose metadata requires `pandas<3,>=1.4.0`.
The `constraints-3.3.1` file that `airflow_src/requirements_airflow.txt` pins against requires `pandas==3.0.5`.

Verified: installing streamlit 1.55.0 into a pandas-3.0.5 env silently downgrades pandas to 2.3.3.

Consequence: `.github/workflows/branch-checks.yaml` installing webapp + airflow deps into one env
(the shortcut its own comment acknowledges) stops being merely imprecise and becomes wrong — whichever
step installs last wins, and one of the two test suites runs against the wrong pandas.
Fixed in this working tree by splitting the CI job into two venvs.

Note the production containers were never affected: the webapp image installs only
`webapp/requirements_webapp.txt`, and has zero Airflow imports.

## 2. `AIRFLOW3_A_PREP_CHANGES.md:232` states a wrong fact 🟡

> "the modules use `from __future__ import annotations`, so they are never evaluated"

`grep -L "from __future__ import annotations" airflow_src/dags/impl/*.py` lists **every** file in that
directory. Only the DAG files at `airflow_src/dags/*.py` carry the future import. The `ti: TaskInstance`
annotations in `dags/impl/*.py` *are* evaluated at import time.

This does not change the conclusion (the annotation is cosmetic either way), but it was the stated
reason for declining §4.3, so the reasoning behind that decision was wrong.

## 3. `AIRFLOW3_B_MIGRATION_GUIDE.md:92-95` assumes a static API token that does not exist 🔴

Doc B §3.2 proposes `_API_TOKEN = os.environ["ALPHAKRAKEN_AIRFLOW_API_TOKEN"]` for the REST API v2 call.
Airflow 3.3.1 has no static API tokens: `POST /auth/token` mints a JWT whose lifetime is
`AIRFLOW__API_AUTH__JWT_EXPIRATION_TIME` (default 86400s). A token baked into a long-running worker's
environment would stop working after a day and take the whole DAG-chaining spine down with it.

## 4. A REST-API rewrite of `trigger_dag_run` would silently kill a rollback path 🔴

`airflow_src/dags/impl/watcher_impl.py:345` catches `DagNotFound` to delete the just-inserted raw file
from MongoDB when the target DAG does not exist — the comment there says that without it "the file would
need to be removed from the DB manually".

Neither doc B §3.2 nor §8 mentions it. `requests`/the Task SDK surface a missing DAG as an HTTP 404,
not as `DagNotFound`, so a literal implementation of doc B's snippet leaves that `except` clause dead
and the rollback never runs. Handled in this working tree by re-raising `DagNotFound` on a 404.

## 5. `metrics_calculator.py` import block fails `ruff check --select I` on HEAD 🟢

`airflow_src/plugins/metrics/metrics_calculator.py:6` — `I001 Import block is un-sorted or un-formatted`,
caused by the commented-out import at line 16 sitting inside the import block. Pre-existing at `4af6de56`

## 6. `AIRFLOW3_B_MIGRATION_GUIDE.md:26-30` names three versions that do not resolve 🔴

The version table in doc B §2 does not match `constraints-3.3.1/constraints-3.11.txt` (fetched and
diffed, 2026-08-26):

| Package | doc B §2 | constraints-3.3.1 |
|---|---|---|
| `apache-airflow-providers-amazon` | 9.35.0 | **9.34.0** |
| `apache-airflow-providers-standard` | 1.18.0 | **1.17.0** |
| `apache-airflow-providers-ssh` | 6.0.1 | 6.0.1 |
| `apache-airflow-providers-fab` | 3.8.0 | 3.8.0 |

Because every line in `airflow_src/requirements_airflow.txt` carries `--constraint <that file>`, a pin
that disagrees with the constraint file is a hard resolution failure, not a preference.

Note `apache-airflow-providers-standard==1.18.0` was already merged for Airflow 2.11 in PR A1
(`2c534888`, doc A §1). It is fine on 2.11 but must drop to 1.17.0 as part of the 3.3.1 flip.

Amazon 9.35.0 in particular surfaces as a second-order conflict, which is how this was found:
`9.35.0` requires `sagemaker-studio>=1.0.25,<1.1.0`, while the repo pins `sagemaker-studio==1.0.23`
(`requirements_airflow.txt:9`) — so pip reports the sagemaker pin as the culprit, not the amazon pin.
The constraint file pins `sagemaker_studio==1.0.27`.

Full resolution of the corrected pin set verified with
`uv pip compile --python-version 3.11 -c constraints-3.3.1.txt`: 187 packages, no conflicts.

## 7. `pandas` is not a dependency of `apache-airflow` — in either version 🔴

Checked the installed metadata of both releases:

```
apache-airflow 2.11.0 -> ["pandas>=1.2.5,<2.2; extra == 'pandas'", ...]
apache-airflow 3.3.1  -> []                       # and apache-airflow-core: []
```

pandas is an **extra** in 2.x and absent from core in 3.x. Nothing in `requirements_airflow.txt` or
`shared/requirements_shared.txt` requires it either, yet `plugins/metrics/metrics/{alphadia,base,diann,msqc,skyline}.py`
all `import pandas`. It has therefore only ever been present because the `apache/airflow:2.11.0` base
image happened to ship it — exactly what the comment at `misc/requirements_development.txt:8` says.

Whether `apache/airflow:3.3.1` still ships pandas could not be verified here (no docker in this
sandbox). If it does not, every metrics task fails with `ModuleNotFoundError: No module named 'pandas'`
— at runtime only, with no parse-time or unit-test signal, since the test envs install pandas separately.

Removed the bet: `pandas==3.0.5` is now pinned explicitly in `requirements_airflow.txt`.

## 8. `AIRFLOW3_B_MIGRATION_GUIDE.md:217-218` conflates two different URLs 🔴

Doc B §4.2 prescribes both keys pointing at the compose service name:

```yaml
AIRFLOW__CORE__EXECUTION_API_SERVER_URL: 'http://airflow-webserver:8080/execution/'
AIRFLOW__API__BASE_URL: 'http://airflow-webserver:8080'
```

They are not the same kind of URL, and only the first one is internal.

**`[api] base_url` is the externally visible URL.** Verified in 3.3.1: it feeds the login redirect
(`api_fastapi/auth/managers/simple/routes/login.py:89`), the cookie path scoping
(`api_fastapi/app.py:56`), and `log_url` / `mark_success_url` on task instances
(`models/taskinstance.py:818`). Setting it to a compose service name hands the *browser* a hostname it
cannot resolve — the symptom is Firefox reporting "Server Not Found: airflow-apiserver:8080" after login.
Airflow 2's equivalent (`[webserver] base_url`) was never set in this repo, so this is a regression
introduced purely by following doc B.

**`[core] execution_api_server_url` is internal, but the service name is still wrong for production.**
The compose service name only resolves inside one compose project on one host. This deployment
deliberately splits `infrastructure` and `workers` across machines (cf. `docs/deployment.md`
"On the PC (VM) hosting the workers"), which is why `POSTGRES_HOST` / `MONGO_HOST` are env vars.
On 2.11 workers reached the metadata DB directly and never needed the webserver; on 3.x every task
needs the Execution API, so a hardcoded service name means **every task on every remote worker fails
immediately**. This would have passed the `--profile local` smoke test and only broken in sandbox/production.

Both are now env vars, following the existing `*_HOST` convention: `AIRFLOW_APISERVER_HOST` (internal,
worker → api-server) and `AIRFLOW_BASE_URL` (external, browser → UI).

## 9. The base image's python version was never pinned, and Airflow 3 moved it 🔴

`airflow_src/Dockerfile:4` used `FROM apache/airflow:${AIRFLOW_VERSION}` — the untagged variant, which
follows whatever python Airflow declares default for that release. Resolved via the Docker Hub API by
digest comparison:

| tag | default python |
|---|---|
| `apache/airflow:2.11.0` | **3.12** |
| `apache/airflow:3.3.1` | **3.13** |

Meanwhile every line of `requirements_airflow.txt` pinned `--constraint .../constraints-3.11.txt`.
So the constraint file has *never* matched the image interpreter (3.11 constraints into a 3.12 image),
and the migration silently widened the gap to 3.13. Confirmed from a running container:
`/home/airflow/.local/lib/python3.13/site-packages/...` in the api-server traceback.

`AIRFLOW3_B_MIGRATION_GUIDE.md:14` states "Python **3.11 stays** — 3.3.1 supports 3.10-3.14 and
`constraints-3.11.txt` exists for it. No interpreter bump needed." The constraint file existing is not
the same as the image using it; the interpreter was 3.12 before and 3.13 after, regardless.

Resolved by pinning both ends to 3.13: `apache/airflow:3.3.1-python3.13` and `constraints-3.13.txt`.
For the record, this is *not* a likely cause of arbitrary breakage: only **12 of 699** pins differ
between `constraints-3.11.txt` and `constraints-3.13.txt` for 3.3.1, and none of them are in the
Flask/FastAPI stack (the differences are `numpy` 2.4.6 vs 2.5.1 plus python-version-gated backports
such as `backports.tarfile` and `importlib-resources`). It is a determinism problem, not a smoking gun.

Worth settling properly, since the pytz gap widens from "identical" on 2.11 to "a year apart" on 3.3.1.

## 11. Two Airflow-3 breakages that only show up with a real 2.11 database / api-server 🔴

Neither is visible from unit tests, `dags reserialize`, or `airflow config lint`. Both were hit on the
first `--profile local` bring-up.

### 11a. Plugins-folder modules can no longer import from the DAGs folder

`airflow_src/plugins/callbacks.py:8` did `from impl.processor_impl import ...`, i.e. a plugins-folder
module reaching into the DAGs folder. In Airflow 2, `settings.prepare_syspath()` put **both** folders on
`sys.path` in every process. In 3.3.1 the function is `settings.prepare_syspath_for_config_and_plugins()`
(`settings.py:716`) and adds only `config/` and `PLUGINS_FOLDER` — the DAGs folder is added by the DAG
processor, which the api-server no longer runs. Result:

```
plugins_manager._load_plugins_from_plugin_directory -> /opt/airflow/plugins/callbacks.py
ModuleNotFoundError: No module named 'impl'
```

`AIRFLOW3_A_PREP_CHANGES.md:272` records this as "Still work. ... confirmed by the clean parse" — the
clean parse only exercised the DAG-processor path, which is exactly the one that still has both folders.
The rename of the function is the tell.

Reproduced and fixed in isolation (`plugins_manager.get_import_errors()` with the DAGs folder off
`sys.path`): before `{'callbacks.py': "No module named 'impl'"}`, after `NONE`.

**The follow-on error is badly misleading.** `plugins_manager.py:253-255` does
`sys.modules[spec.name] = mod` *before* `loader.exec_module(mod)`, and the `except` branch records the
import error without removing the entry. `mod_name` is the file stem, i.e. `callbacks`. So after the
failed plugin import, `sys.modules["callbacks"]` holds a half-initialised, empty module, and the DAG
parse that follows never touches the filesystem:

```
File "/opt/airflow/dags/acquisition_handler.py", line 12, in <module>
    from callbacks import on_failure_callback
ImportError: cannot import name 'on_failure_callback' from 'callbacks' (/opt/airflow/plugins/callbacks.py)
```

The named path is the *poisoned* module's `__file__`, not the file being imported — so a container still
running the pre-fix image reports a symptom that points at the wrong file and looks like a different bug.

Fixed by `mv airflow_src/plugins/callbacks.py airflow_src/dags/callbacks.py` (+ its test). `callbacks.py`
was the only plugins-folder module importing from `dags/`, and the repo defines no `AirflowPlugin`
subclass at all — the plugins folder is used purely as a shared-code path — so nothing needed it to live
there. The one-line alternative is adding `${AIRFLOW_HOME}/dags` to `PYTHONPATH` in the Dockerfile, which
restores Airflow 2 behaviour but keeps the api-server importing mongoengine/pandas/docker at startup.

### 11b. The `session` table cannot be carried across the 2 -> 3 boundary

Same table, same class name, incompatible payloads:

| | class | serializer |
|---|---|---|
| 2.11 | `airflow.www.session.AirflowDatabaseSessionInterface` | flask-session default (**pickle**) |
| 3.3.1 | `airflow.providers.fab.www.session.AirflowDatabaseSessionInterface` | `_LazySafeSerializer` (**msgpack**/`msgspec`) |

`airflow db migrate` does not rewrite the rows, so every session written by 2.11 is undecodable and
`GET /auth/login/` returns 500 with `msgspec.DecodeError: MessagePack data is malformed`.

Doubly confusing to diagnose: Flask's own 500 handler then fails with
`AssertionError: The session has not yet been opened`, so the visible tail of the traceback says nothing
about the real cause, which is further up the log.

Fix is to purge the table (`DELETE FROM session;`, or `airflow db clean --table session` — it is a
registered cleanup table with `recency_column_name="expiry"`) **and** clear the browser cookie for the
Airflow host. Nothing is lost; users log in again. Added as a mandatory step to
`AIRFLOW3_B_MIGRATION_GUIDE.md` §5, which did not mention it.
